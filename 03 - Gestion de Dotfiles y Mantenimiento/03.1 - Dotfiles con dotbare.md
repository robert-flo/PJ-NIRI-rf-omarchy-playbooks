# 📦 Gestión de Dotfiles con dotbare

> [!NOTE]
> **Navegación:**
> * Anterior: [[02.4 - Referencias de Temas, Wallpapers y Recursos|Referencias de Temas y Recursos]]
> * Siguiente: [[03.2 - Validacion en Usuario Limpio (Testbench)|Validación en Usuario Limpio (Testbench)]]
> * Posterior: [[03.3 - Snapshots de Home con Btrfs|Snapshots de Home con Btrfs]]
> * Volver a: [[00 - Indice General (MOC)|Índice General]]

Este playbook describe el flujo de trabajo para versionar, auditar y compartir públicamente la configuración completa del escritorio Niri y Clavis utilizando **[dotbare](https://github.com/kazhala/dotbare)** (un gestor interactivo basado en repositorios Git *bare* sobre `$HOME` con soporte de `fzf`).

---

> [!IMPORTANT]
> **Modelo operativo (máquina de referencia, 2026-10-12)**
> - Repositorio: [robert-flo/niri-dotfiles](https://github.com/robert-flo/niri-dotfiles), rama `master` = **verdad**.
> - `niri` = **producción**; `sura` = **pruebas visuales**, desechable. Ambos usuarios llevan el repo con dotbare en `~/.cfg`.
> - Todo cambio de configuración de usuario: se prueba en `sura` → PR a `master` → `niri` hace `dotbare pull`. Si en `sura` sale mal, se descarta (o se borra `sura` y se recrea desde el repo).
> - Lo que pueda vivir en los dotfiles vive en los dotfiles (por ejemplo, el arranque de `key clipboard --daemon`). Lo propio de cada máquina (`outputs.kdl`) queda fuera del repo.
> - El repo ya existe: en una reinstalación **no se repiten las secciones 2–5** (crear y publicar); se usa la sección 0. Las secciones de creación quedan como referencia.

## 0️⃣ Restaurar en una Máquina Nueva (`niri` y `sura`)

Requisitos: módulo 01 completo (niri-edge, `key-cli` del fork, Clavis), temas MacTahoe (02.1) y `dotbare` instalado (sección 1). Ejecutar desde el usuario administrador para cada usuario:

```bash
REPO_URL="https://github.com/robert-flo/niri-dotfiles.git"
cd /tmp   # sudo -u desde un directorio que los usuarios objetivo puedan leer
for TARGET_USER in niri sura; do
    TARGET_HOME="$(getent passwd "$TARGET_USER" | cut -d: -f6)"
    TARGET_UID="$(id -u "$TARGET_USER")"

    # 1. Clonar y hacer checkout (respalda conflictos en ~/.local/share/dotbare/)
    sudo -u "$TARGET_USER" env HOME="$TARGET_HOME" DOTBARE_DIR="$TARGET_HOME/.cfg" DOTBARE_TREE="$TARGET_HOME" \
        bash -c "cd ~ && dotbare finit -y -u '$REPO_URL' </dev/null"

    # 2. finit -u deja el repo bare sin refspec ni upstream: sin esto `dotbare pull` no ve origin/master
    G="sudo -u $TARGET_USER git --git-dir=$TARGET_HOME/.cfg --work-tree=$TARGET_HOME"
    $G config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'
    $G config status.showUntrackedFiles no
    $G fetch origin && $G branch -u origin/master master

    # 3. Post-instalación (gsettings, servicios Clavis, Matugen, validación)
    sudo -u "$TARGET_USER" env HOME="$TARGET_HOME" XDG_RUNTIME_DIR="/run/user/$TARGET_UID" \
        bash -c '~/.local/bin/niri-dotfiles-postinstall'
done
```

> [!WARNING]
> **Antes de alinear un usuario que ya tiene configuración**, toma un snapshot de `/home` ([[03.3 - Snapshots de Home con Btrfs|03.3]]). `finit -u` reemplaza todos los archivos versionados; los anteriores quedan en `~/.local/share/dotbare/`. En la máquina de referencia: `/home/.snapshots/home-2026-10-12-pre-dotbare-niri`.

> [!NOTE]
> - **Pantallas:** `config.kdl` termina con `include optional=true "outputs.kdl"`. Cada máquina crea su `~/.config/niri/outputs.kdl` (ver [[04.1 - Fix Parpadeo Intel i915 (FIFO Underrun & SAGV)|04.1]]); si no existe, niri usa el modo preferido del monitor.
> - **`sura` siempre muestra 2 archivos modificados:** el postinstall reescribe `/home/niri` → `/home/sura` en `~/.config/clavis/config.json` y `~/.config/obsidian/obsidian.json`. Es esperado; no los incluyas en commits hechos desde `sura`.
> - **Estado visual que restaura el repo:** modo claro de Clavis, cursor `MacTahoe-cursors` a 128, wallpaper `statindet/wallhaven-rq6yqm.jpg`, perfil de Thunderbird con LiquidBird.

> [!TIP]
> **Credenciales.** `niri` solo necesita leer (repo público). Para hacer push desde `sura` o `niri`, inicia sesión una vez dentro de cada usuario con `gh auth login` y `gh auth setup-git`. Mientras tanto, el usuario administrador puede operar con su propio `gh` sobre un clon temporal (como se hizo el 2026-10-12).

## 🎯 Por qué dotbare

1. **Sin enlaces simbólicos frágiles:** Los archivos residen directamente en `$HOME` y `~/.config/`, evitando estructuras intermedias que complican la edición.
2. **Repositorio Bare (`~/.cfg`):** El repositorio Git no contiene un directorio de trabajo normal visible, manteniendo el home limpio.
3. **Control granular:** Solo los archivos explícitamente agregados con `dotbare add` son seguidos por Git (`status.showUntrackedFiles=no`).

## 1️⃣ Preparación

Instalar `dotbare` desde AUR (depende de `fzf`):

```bash
yay -S --needed dotbare
```

---

## 2️⃣ Inicialización del Repositorio Bare

Ejecutar bajo la identidad del usuario objetivo (ej. `niri`):

```bash
TARGET_USER="${1:-$USER}"
TARGET_HOME="$(getent passwd "$TARGET_USER" | cut -d: -f6)"

sudo -u "$TARGET_USER" env HOME="$TARGET_HOME" DOTBARE_DIR="$TARGET_HOME/.cfg" DOTBARE_TREE="$TARGET_HOME" \
  GIT_CONFIG_PARAMETERS="'init.defaultBranch=master'" bash -c 'cd ~
# Inicializar repositorio bare
dotbare finit -y </dev/null

# Configurar identidad de Git (ajusta con tus datos públicos)
git --git-dir=.cfg config user.name  "Tu Nombre"
git --git-dir=.cfg config user.email "tu_email@ejemplo.com"
'
```

> [!IMPORTANT]
> **Qué trackear:** Archivos de configuración de Niri, Clavis, temas, scripts, configs de aplicaciones y wallpapers seleccionados.
> **Qué EXCLUIR:** Backups `*.bak*`, cachés, estados de sesión (`.local/state`), notas personales de Obsidian, perfiles con credenciales de correo/Thunderbird y salidas generadas de Matugen (salvo aquellas requeridas para validar sintaxis inicial).

## 4️⃣ Auditoría Estricta de Secretos (Antes de Compartir)

Antes de hacer público el repositorio o empujar cambios a GitHub, es indispensable escanear en busca de credenciales, claves SSH o tokens:

```bash
sudo -u "$TARGET_USER" bash -c 'cd ~; git --git-dir=.cfg --work-tree=. ls-files -z | xargs -0 rg -n -i -I \
  -e "ghp_[A-Za-z0-9]{20,}" -e "github_pat_" -e "-----BEGIN .*PRIVATE KEY" \
  -e "(password|passwd|secret|api[_-]?key|token)\s*[=:]\s*\S{6,}" -e "@(gmail|outlook|hotmail)\."'
```

*Si la búsqueda arroja cero coincidencias no autorizadas, el árbol está limpio para ser compartido.*

## 5️⃣ Commit y Publicación en GitHub

```bash
# 1. Crear el commit inicial
sudo -u "$TARGET_USER" bash -c 'cd ~; git --git-dir=.cfg --work-tree=. commit -m "Initial commit: niri + Clavis desktop configuration"'

# 2. Crear repositorio público en GitHub con GitHub CLI (gh)
gh repo create niri-dotfiles --public --description "niri + Clavis (Quickshell) desktop dotfiles, managed with dotbare"

# 3. Vincular y enviar a la rama principal
sudo -u "$TARGET_USER" bash -c 'cd ~
git --git-dir=.cfg remote add origin https://github.com/<tu_usuario>/niri-dotfiles.git
git --git-dir=.cfg push -u origin master
'
```

## 6️⃣ Flujo de Trabajo Diario (`sura` → `niri`)

Variables (ya en el entorno si sigues la sección 0; si no, añádelas a `~/.config/fish/config.fish`):

```bash
set -gx DOTBARE_DIR "$HOME/.cfg"
set -gx DOTBARE_TREE "$HOME"
```

**1. En `sura` (pruebas):**
```bash
dotbare checkout -b ajuste/esquinas        # rama auxiliar, nunca commit directo a master
# ... editar y probar visualmente en la sesión Niri de sura ...
dotbare fadd                               # elegir archivos (no config.json ni obsidian.json, ver nota de la sección 0)
dotbare commit -m "Ajustar curvatura de esquinas"
dotbare push -u origin ajuste/esquinas
gh pr create --repo robert-flo/niri-dotfiles --base master --head ajuste/esquinas
```

**2. Antes de mergear:** rebasar la rama sobre el `master` más reciente (`dotbare fetch origin && dotbare rebase origin/master`), mergear el PR y borrar la rama local y remota. Volver `sura` a `master`:
```bash
dotbare checkout master && dotbare pull --ff-only
dotbare branch -d ajuste/esquinas
```

**3. En `niri` (producción):**
```bash
dotbare pull --ff-only
~/.local/bin/niri-dotfiles-postinstall     # solo si el cambio toca gsettings, servicios o colores
```

**Si la prueba sale mal en `sura`:** `dotbare checkout master && dotbare reset --hard origin/master`. Si `sura` quedó irreconocible, se borra el usuario y se recrea con [[03.2 - Validacion en Usuario Limpio (Testbench)|03.2]] + sección 0.

## 7️⃣ Script de Post-Instalación en Máquinas Nuevas

Al clonar los dotfiles en otra máquina o usuario, ciertos valores no viven en archivos versionados (GSettings, servicios de usuario, rutas absolutas, colores generados). Los aplica `~/.local/bin/niri-dotfiles-postinstall`, **versionado en el propio repo** (esa es la versión vigente; no se copia aquí para que no diverja). Es idempotente y hace:

1. Adapta `/home/niri` → `$HOME` en `~/.config/clavis/config.json` y `~/.config/obsidian/obsidian.json`.
2. `gsettings`: tema GTK `MacTahoe-Dark`, iconos `MacTahoe-dark`, botones a la izquierda, y modo claro/oscuro y cursor **leídos de Clavis** (`theme.mode` en `config.json`, `clavis/cursor.kdl`).
3. Habilita `clavis-shell.service` y `clavis-clipboard.service`.
4. Crea `~/Pictures/mpv`.
5. Genera los colores Matugen desde el wallpaper de Clavis (focus ring de niri, fcitx5, fish).
6. Valida `config.kdl` con `niri validate`.

Fuera de una sesión gráfica avisa de lo que no pudo aplicar (sin bus D-Bus); basta con exportar `XDG_RUNTIME_DIR=/run/user/<uid>` (usuarios con linger) o repetirlo dentro de la sesión.
